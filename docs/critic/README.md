# The critic system

A "random gamer" critic for Woolgather. The critic is Sam, a player who writes blunt Steam reviews
(`tests/critic/persona.md`). Sam only ever sees footage of the game and a one-line store blurb: never
the code, the design notes, this repo or the reasons behind any choice. Sam scores eight things from
1 to 10 (look, readability, feel, fun, variety, progression, want to keep playing, would wishlist) and
lists the five worst problems with a severity, as JSON.

## The critics

| Critic | Sees | Reply file |
| --- | --- | --- |
| Gemini, video mode (`tests/critic/gemini.mjs --video`) | the whole `video.mp4` | `gemini.json` |
| Gemini, images mode (`tests/critic/gemini.mjs --images`) | the named stills (or any JPEGs), inline | `gemini-stills.json` |
| A Claude subagent | the contact sheets (`sheets/sheet-*.jpg`, a frame every 2.5 s of play) | `video-critic.json` |
| A Claude subagent | the named stills (`stills/*.jpg`) | `stills-critic.json` |

The Gemini critics run only when `GEMINI_API_KEY` is set (otherwise they write `*-skipped.json` and
exit 0). In images mode the MEDIA line lists the file names in capture order ("Below are screenshots
from the game, in order: title.jpg, herding-early.jpg, ..."), so stills are named for what a player
would call the moment. `r00-baseline` also keeps a first video verdict from `gemini-3.1-pro-preview`
(`gemini-pro-video.json`) for comparison with the default Flash model.

Each critic gets the persona prompt with `{{BLURB}}` and `{{MEDIA}}` filled in. The Claude critics are
spawned by the session running the round, with only the persona prompt and the image paths (no repo
context); `node tests/critic/gemini.mjs --print-prompt --blurb "..." --media "..."` prints the filled-in
prompt. Their JSON replies are saved into the round's folder under the names above, with a
`"critic"` field naming them.

## Commands

```sh
# 1. Play a build on a virtual clock and record it (about real time; a whole evening is 4-6 minutes)
node tests/critic/capture.mjs --dist dist --label r01-something --scenario classic
#    options: --width 1280 --height 720 --fps 20 --minutes 9 --seed 11 --diff standard --every 2.5

# 2. Contact sheets from the periodic frames (4 x 3 tiles, each labelled with its game time)
node tests/critic/sheets.mjs --dir test-results/critic/r01-something

# 3. Copy stills, sheets, meta.json and marks.json into docs/critic/r01-something/
node tests/critic/publish.mjs --label r01-something

# 4. The Gemini critics: the video, then the stills (each skips cleanly, exit 0, without a key)
node tests/critic/gemini.mjs --video test-results/critic/r01-something/video.mp4 \
  --out docs/critic/r01-something --blurb "Woolgather. You are Pip, a border collie. Herd the flock home before nightfall."
node tests/critic/gemini.mjs --images docs/critic/r01-something/stills \
  --out docs/critic/r01-something --blurb "Woolgather. You are Pip, a border collie. Herd the flock home before nightfall."

# 5. The Claude critics (spawned by the session), then the scoreboard
node tests/critic/report.mjs
```

The key is read from the environment or from `.env.local` at the repo root (`GEMINI_API_KEY=...`,
gitignored). By default the critic asks `gemini-3.8-flash` and falls back to `gemini-flash-latest`,
then `gemini-3.1-pro-preview`, when a model is unknown or rate limited; each reply records which one
answered (`model`, `models_tried`) and how long each step took (`timing`). `GEMINI_MODEL` (or
`--model`) names a single model instead. The video upload is the capture's own `video.mp4` (about
57 MB for a whole evening at 720p, well under the Files API limit; the upload is most of the call's
time); Gemini samples video at about one frame per second, so the 20 fps capture is plenty. Images
are sent inline, each kept under about 1.5 MB. Any em dash in a critic's prose is saved as a spaced
hyphen (house rule).

`capture.mjs` serves the build with its own small static server on a free port (no Vite, nothing is
built), so it can film a frozen build while `src/` is being changed. It never uses ports 5317 or 4317.

## Where things go

- `test-results/critic/<label>/` (gitignored): `video.mp4`, `stills/`, `frames/` (640 px periodic
  frames and `index.json`), `sheets/`, `marks.json` (game events and stills with video time and the
  day clock), `meta.json` (outcome, sheep home and lost, duration, console errors), `console.txt`.
- `docs/critic/<label>/` (committed): stills (re-encoded, 1280 px), sheets, `meta.json`, `marks.json`
  and the critics' JSON replies. No video.
- `docs/critic/SCOREBOARD.md`: every round's scores and one-line reviews, regenerated by `report.mjs`.

"Game time" everywhere (file names, tile labels, `video_t` in marks) is the capture's virtual clock,
which is also the video's timestamp; `game_t` / `day_t` is the game's own day clock, which starts when
the evening starts and stops at the result card.

## Adding a scenario

Scenarios live in `tests/critic/scenarios.mjs` as `export const scenarios = { name: async (ctx) => {...} }`.
Add a key and run `capture.mjs --scenario name`; `capture.mjs` needs no change. The page starts on the
title screen with the virtual clock running. The context gives:

- `page` (Playwright; `window.__WG` test hooks: `state()`, `drain()`, `jumpTo(t)`, `teleportDog(x, z)`,
  `setTimeScale(k)`), `bot` (the HerdBot: `await bot.step(state, 1 / fps)` every frame, `await bot.release()`)
- `frame()` one frame into the video, `frames(seconds)`, `still(name)`, `mark(label, info)`, `state()`
- `fps`, `opts` (the command-line options), `log`, `time()` (game seconds so far), `overTime()` (past
  `--minutes`), `dist(a, b)`

The `classic` scenario is the template: three seconds on the title (still `title`), Enter, the bot plays
the whole evening, stills at `herding-early` (20 s in), `wolf-near` (a wolf stalking within 35 m of Pip),
`snatch` (a wolf dragging a sheep), `sunset` (half the day gone), `dusk` (85%), and `end-card` two
seconds after the result.
